# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

LifeManager is a personal life management tool: the goal is to help users manage different areas of their life — starting with personal finances (transactions, categories, monthly summaries) and eventually habits and other areas — from one place. This repo (`LifeManagerFront`) is the frontend SPA; it consumes the sibling backend project `LifeManager` (`../LifeManager`, a .NET API), whose domains so far are Auth, Users, Categories, Transactions, and MonthlySummaries.

## Project state

This is a Vite + React + TypeScript app (`lifemanagerfront`). The Vite starter demo content has been stripped out. Routing (`react-router-dom`) is wired up in `App.tsx`: `/auth` (public), `/home`, `/finance/*` and `/habits/*` (protected), and everything else (`*`, including `/`) redirecting to `/home` — see "Route guards" below. Every module talks to the backend API; Vitest covers utils, validation schemas and formatters.

## Architecture notes

- Entry point: `src/main.tsx` mounts `App` from `src/App.tsx` into `#root` in `index.html`.
- Routing uses `react-router-dom`. `App.tsx` owns the top-level `<BrowserRouter><Routes>...</Routes></BrowserRouter>` shell — add feature routes there, pointing at page components from each feature's `pages/` folder (see below), e.g. eventually `<Route path="/auth" element={<AuthPage />} />`.
- TypeScript is split via project references (`tsconfig.json` → app + node configs) rather than a single flat config; `tsc -b` (used in `npm run build`) respects this and only type-checks, since `noEmit` is set — Vite/esbuild handles actual transpilation.
- `verbatimModuleSyntax` is enabled, so type-only imports must use `import type { ... }`.
- Linting uses Oxlint (Rust-based, fast) instead of ESLint. The current config (`.oxlintrc.json`) enables `react`, `typescript`, and `oxc` plugins but not type-aware linting — see README.md for how to enable `oxlint-tsgolint` and type-aware rules if needed later.
- Static assets referenced by URL (favicon, sprite icons) live in `public/`; assets imported directly in components go in `src/assets/` (currently empty — the demo images that lived here were removed along with the Vite starter content).
- Design tokens (color, typography, spacing, radius, shadows, motion) live as CSS custom properties in `src/shared/styles/tokens/*.css`, sourced from a Claude Design handoff — see the folder-structure section below. `src/index.css` (imported once, in `main.tsx`) is just the `@import` list for these plus `shared/styles/base.css`; don't add component-specific rules there.
- Icons use `lucide-react`. The shared `Icon` component (`src/shared/components/Icon/Icon.tsx`) wraps a small explicit name→icon registry rather than importing the whole library — add new icons to that registry as they're needed, don't import `lucide-react` icons directly elsewhere.
- Dark mode is real, not decorative: `src/shared/hooks/useTheme.ts` toggles `data-theme="dark"` on `<html>` and persists the choice in `localStorage`; all color tokens have light/dark values keyed off that attribute.
- HTTP goes through `src/shared/services/httpClient.ts` (`apiRequest`), which attaches `Authorization: Bearer <token>` from `src/shared/services/tokenStorage.ts` (access token in `sessionStorage`) when present.
- **API base URL:** `VITE_API_BASE_URL` — `https://localhost:7233` in dev (`.env`, from `.env.example`), **empty** in production (`.env.production`, committed). Production is served by Firebase Hosting (`firebase.json`), which rewrites `/api/**` to the Cloud Run service, so the app and the API share one origin: no CORS, and the refresh cookie (named `__session`, the only cookie Hosting forwards) is first-party. Deploy with `npm run deploy` (README); the backend side is in `../LifeManager/docs/deploy.md`.
- **Token refresh:** the access token lasts 15 min; the HttpOnly `refreshToken` cookie renews it.
  - **When:** on a `401` from any non-`/api/Auth/*` path, `apiRequest` calls `refreshAccessToken()` (`shared/services/authSession.ts`, `POST /api/Auth/Refresh`) and retries the request once with the new token. Auth paths are excluded because a 401 from Login means wrong credentials.
  - **Concurrency:** `refreshAccessToken` is single-flight per tab and serialized across tabs with a Web Lock (`navigator.locks`, `lm-token-refresh`). The backend rotates the token and treats reuse of an old one as theft, revoking the whole session, so two tabs must never refresh with the same cookie at once.
  - **Refresh rejected** (expired, revoked, or past the 30-day session cap): the token is cleared, `refreshAccessToken()` fires `emitSessionExpired()` once (`shared/services/sessionEvents.ts`), and every pending `apiRequest` rejects with `SessionExpiredError`.
  - **Redirect:** `useSessionExpiredRedirect` (mounted via `SessionExpiredListener` in `App.tsx`, inside the router) shows `common:sessionExpiredToast` and navigates to `/auth`.
  - **Callers' error UI:** mutation handlers skip their own error UI with `isSessionExpiredError(err)`. A network error during refresh rejects with the usual connection error and does **not** sign the user out.
- **Route guards** — in `App.tsx`, every signed-in screen sits under the `shared/components/ProtectedRoute/` layout route and `/auth` under `shared/components/PublicOnlyRoute/`. New authenticated routes go inside `ProtectedRoute`.
  - `ProtectedRoute`: with an access token it renders the `<Outlet />` right away. Without one (a new tab or a reload) it renders nothing while `restoreSession()` (`shared/services/authSession.ts`) tries the refresh cookie. Success renders the screen; rejection redirects to `/auth` with `state.from` and **no** session-expired toast (the user never signed in, or just signed out). A network error shows the connection error modal and also redirects (fails closed).
  - `restoreSession()` shares the single-flight/Web Lock with `refreshAccessToken()` but never emits `sessionExpired`; only `refreshAccessToken()` (a 401 mid-use) announces it.
  - `PublicOnlyRoute`: a token in `sessionStorage` redirects `/auth` to `/home`. It checks the token only, with no refresh call.
  - `LoginForm` navigates to `location.state.from` (falling back to `/home`) with `replace`, so the user returns to the screen they were bounced from.
- **Paged listings** — every list endpoint is paginated, searched and sorted on the backend (offset pagination: `?page=&pageSize=&search=&sortDirection=Asc|Desc`, `pageSize` ≤ 100), returning the envelope typed as `PagedResponse<T>` in `shared/types/Paging.ts`. Never fetch a whole collection to filter/sort/slice it in the browser. Pattern (see `finance/hooks/useCategories.ts`): the feature hook owns the query state, debounces the search input with `shared/hooks/useDebouncedValue.ts`, fetches with an `AbortController`, keeps the last page on screen while the next loads (`isFetching`), and refetches after mutations; the list component is presentational and renders `shared/components/Pagination/` (windowed page numbers via `shared/utils/getPageItems.ts`; the caller passes the translated range label). Backend search is accent/case-insensitive: it matches a persisted normalized column (`SearchText.Normalize` in the Domain) through a `pg_trgm` GIN index.
- User preferences (theme + language) are persisted in the backend (`/api/UserPreferences`, enums as strings `Light|Dark`, `PTBR|EN` — mapped in `shared/utils/userPreferencesMapper.ts`). On login, `LoginForm` calls `loadAndApplyUserPreferences()` (`shared/services/userPreferencesService.ts`) before navigating, which applies them via `applyTheme`/`applyLanguage` (exported from `useTheme.ts`/`useLanguage.ts`) so the hooks initialize from them. `Header` calls `useUserPreferencesSync(theme, language)`, which saves changes with an 800 ms debounce (skips unchanged values, flushes on unmount) and returns `{ flush }` to save a pending change immediately. The debounced save always goes through `apiRequest`, even with no access token in `sessionStorage` (e.g. a new tab), so a 401 refreshes it from the cookie; only the leaving flushes (unmount and `flush()`) are skipped without a token, since then the user is signing out and a failed refresh would show the session-expired toast.
- **Current user** — the Header's menu shows the signed-in user's name from `GET /api/Users/Me` via `shared/hooks/useCurrentUser.ts` (fetched on mount with an `AbortController`; the name block is hidden while loading or on failure). It isn't returned by Login on purpose: a new tab or reload gets its token from the refresh cookie and never sees the login response.
- **Logout** — the Header's "Sair" button calls `flush()` (so a still-debounced preference change goes out while the access token is valid; `apiRequest` reads the token synchronously before `fetch`), then `useLogout()` (`shared/hooks/useLogout.ts`: guards double clicks via `isLoggingOut`, shows `common:logoutSuccessToast`, `navigate('/auth', { replace: true })`). The API call lives in `shared/services/authSession.ts` (not `auth/services`, since `shared/` must not import from features): `POST /api/Auth/Logout` revokes the refresh token and deletes its HttpOnly cookie server-side (the backend endpoint is anonymous and idempotent); `clearAccessToken()` runs in a `finally`, so a failed request never blocks signing out locally.

## Internationalization (i18n)

**Every new screen or UI text from now on must ship with i18n already wired up — never land a hardcoded user-facing string, not even "to translate later."** This is part of finishing a feature, not a follow-up cleanup task.

- The app uses `react-i18next` (`i18next` + `react-i18next`), initialized once in `src/i18n/i18n.ts` and imported as a side effect at the top of `src/main.tsx`. Supported languages: `en-US` (default/fallback) and `pt-BR`, tracked by `src/shared/hooks/useLanguage.ts` — mirrors `useTheme.ts`'s pattern (plain hook, `localStorage['lm-language']`, no Context/Provider).
- Every feature owns its own i18next **namespace**, mirroring the per-feature folder convention: strings live in `<feature>/locales/{en-US,pt-BR}.ts` (see `src/auth/locales/`, `src/home/locales/`), and any new namespace must be registered in the `resources`/`ns` list in `src/i18n/i18n.ts`. A string only belongs in the shared `common` namespace (`src/shared/locales/`) if it's rendered from `src/shared/**` or reused verbatim by 2+ features — otherwise it stays in the owning feature's namespace, even if similar wording exists elsewhere.
- In components: `const { t: translate } = useTranslation('<namespace>')` (or an array of namespaces if the component needs more than one), then `translate('namespace:key.path')` — always with the explicit `ns:` prefix, even for a single-namespace call.
- Data-shaped content (e.g. a config array like `HomePage.tsx`'s `MODULES`) can't hold translated text directly, since it's evaluated once rather than re-rendered — store an id/key instead and look the copy up with `translate(...)` inside the component that renders it (see `ModuleCard.tsx`).
- Validation messages (Zod schemas, backend error-code maps) are also evaluated once at import time, so they store translation **keys** as the message and get translated at the render boundary — see `src/auth/validation/userSchemas.ts` and `src/shared/utils/applyApiErrorToForm.ts`.
- When adding a new screen: create its `locales/en-US.ts` + `locales/pt-BR.ts` pair, register the namespace in `src/i18n/i18n.ts`, and translate every string as it's written.

## Responsiveness (mobile-first)

**Phones are the primary target — every screen must work at 360px wide before it's considered done.**

- **Breakpoint:** a single compact breakpoint, `@media (max-width: 768px)` (custom properties can't be used in media queries, so it's a convention). Size touch targets with `@media (pointer: coarse)` and wrap `:hover` styles in `@media (hover: hover)` (hover sticks after a tap) — these depend on the input device, not the width. Keep a hover rule *before* any `:active` rule of the same specificity so the pressed state still wins.
- **Tokens** (`shared/styles/tokens/spacing.css`): page side padding is `--page-gutter` (32px → 16px compact). On touch, `--control-height-sm/md/lg` grow to 36/44/48px, so every control built on them (Button, IconButton, Input, Pagination) gets bigger tap targets for free — don't hardcode control heights. `--app-bottom-inset` is the space taken by fixed bottom chrome (the Finance bottom tab bar sets it via `:root:has(...)`); fixed/bottom elements (Toast, page content) offset by it plus `env(safe-area-inset-bottom)`.
- Full-height roots use `min-height: 100vh; min-height: 100dvh;` (fallback + dynamic viewport), never `100vh` alone.
- Inputs render at 16px on touch (`Input.css`) so iOS doesn't zoom on focus — keep it for any new text field.
- **Modals** go through `shared/components/Dialog/`, which turns into a bottom sheet on compact screens (full-width footer buttons, safe-area padding) — don't build custom modal positioning.
- **Module navigation:** every module uses `shared/components/ModuleSidebar/` (a collapsible sidebar that becomes a fixed bottom tab bar on compact screens and sets `--app-bottom-inset`), through a thin wrapper that passes its translated items (`finance/components/FinanceSidebar/`, `habits/components/HabitsSidebar/`). Its layout pads the content by `--app-bottom-inset`.
- **Lists:** stack toolbars vertically and make search full width on compact screens; never rely on a horizontally scrolling table — show the essential columns as rows/cards. No action may be reachable only by hover.

## Folder structure: feature modules

This frontend mirrors the feature-based organization of its sibling backend project, `LifeManager` (`../LifeManager`), which is a .NET Clean Architecture solution where each layer (Domain, Application, Infrastructure, WebApi) has one subfolder per domain (`Auth/`, `Users/`, ...), each split further by responsibility (`DTOs/`, `Services/`, `Controllers/`, ...).

Since this is a single-layer SPA rather than a layered architecture, each feature gets one folder directly under `src/`, and inside it the responsibility-based subfolders relevant to a frontend module — not a 1:1 mirror of the backend's layers. **Do not create top-level `src/pages`, `src/services`, etc. shared across all features** — those belong inside each feature folder instead.

Per-feature subfolder convention (established with the `auth` module):
- `pages/` — top-level screens for the feature
- `components/` — UI components used by those screens. **One folder per component** (`ComponentName/ComponentName.tsx` + `ComponentName.css`), matching the convention in `shared/components/`. Exception: a `.css` file genuinely shared by several sibling components in the same feature (not a component itself) can live directly under `components/` instead of inside any one of their folders — e.g. `auth/components/AuthForm.css`, shared by `LoginForm/` and `RegisterForm/`.
- `services/` — API calls / business logic (equivalent to the backend's `Services/`)
- `types/` — request/response types (equivalent to the backend's `DTOs/`), **plus feature-wide domain vocabulary used by more than one file** (e.g. `auth/types/AuthMode.ts`, the `'login' | 'signup'` union shared by `AuthPage` and `AuthTabs`). This is *not* where component props types go — a component's own `Props` interface stays colocated in its `.tsx` file, same as everywhere else in React/TS; `types/` is for things that aren't the shape of one component's JSX API.
- `hooks/` — feature-specific custom hooks

Backend concepts intentionally **not** mirrored per feature: `Controllers/` (no frontend equivalent), `Errors/`/`Interfaces/`/`ValueObjects/` (Domain-layer concerns that don't apply to a UI module).

**Exception: `src/shared/`.** Features don't share folders with each other, but they can all depend on `src/shared/` — the frontend equivalent of the `Shared/` folder that already exists in the backend (`LifeManager.Domain/Shared`). It holds design tokens and UI primitives meant to be reused across the whole app (buttons, inputs, icons, colors), not feature-specific code:
- `shared/styles/tokens/` and `shared/styles/base.css` — the design system's CSS custom properties (see Architecture notes above)
- `shared/components/` — one folder per primitive (e.g. `Button/`, `Input/`, `Select/`, `IconButton/`, `Icon/`), each with its `.tsx` and its own `.css`
- `shared/hooks/` — cross-feature hooks (e.g. `useTheme`)

Before adding something new to `shared/`, make sure it's genuinely cross-feature — a component only used by one feature belongs in that feature's `components/`, not here (this is why there's no generic `Card` in `shared/` yet: nothing needs it besides `auth`'s hand-built layout, so it hasn't been extracted).

"Tive uma recaída" opens `components/RelapseDialog/` (shared `Dialog`, `alertdialog`): today/yesterday when yesterday can still take one, and the cost from `utils/relapseCost.ts` (HP and the streak to be lost, or "still within the limit"). `useHabitsToday().setRelapse(item, date, relapsed)` posts or deletes `/api/Habits/{id}/Relapses` **without** optimistic updates (it costs HP), with the same double-tap guard; then the page reloads the profile and shows a toast. `Habit.AlreadyRelapsed`/`RelapseNotFound` just reload, like the check-in codes (`showSaveError`).
  - **Shop** (`/habits/shop`, sidebar item `shop`; `/api/Rewards`): `pages/ShopPage.tsx` is a layout route with two link tabs that passes the outlet context on, `rewards` (the index) → `pages/RewardsPage.tsx` and `redemptions` → `pages/RedemptionsPage.tsx`. `services/rewardService.ts`, `hooks/useRewards.ts` (paged-listing pattern: page, `Active|Archived`, debounced search, sort `Cost|Name` + direction, cheapest first) and the presentational `components/RewardList/` (a card grid, one column on ≤768px: icon, price, "≈ N days of habits" from `hooks/useEarningPace.ts` + `utils/rewardPace.ts`, and a Redeem button that turns into "N coins short" when the outlet context's balance doesn't cover it). `components/RewardFormModal/` (`validation/rewardSchema.ts`, cost typed as text; icon picked from `utils/rewardIcons.ts`, ids stored on the backend, unknown ones fall back to `gift`) + `validation/rewardErrorMap.ts`; "delete" archives (`ArchiveRewardModal`) and archived rewards can be restored. Redeeming goes through `components/RedeemRewardDialog/` (price and balance after); then the page calls `reloadProfile()` and toasts `formatWalletChange`. `InsufficientCoins` shows the error modal and reloads the profile. `hooks/useRedemptions.ts` + `components/RedemptionList/` list the history, newest first; a redemption's Undo shows only when the backend's `canUndo` says so (made today, not undone), so the browser clock is never used.
  - **History & stats:** each `HabitList` row is a stretched link to `/habits/list/:habitId` → `pages/HabitDetailsPage.tsx` (`hooks/useHabitStats.ts`, `GET /api/Habits/{id}/Stats`, `notFound` on `Habit.NotFound`): `components/HabitStatsSummary/` (streak + record, consistency — last 30 days, or last 4 closed weeks for times-per-week habits, with frozen days left out by the backend — and the days kept toward 66), `components/HabitHeatmap/` (13 weeks as calendar columns, Monday on top, laid out by `utils/heatmap.ts`; one color per backend `HabitDayState`, from a kept/protected/failed palette validated with the dataviz skill's checker in both themes; a tapped or hovered day is read out below, and the legend counts the days per state) and the habit's own statement lines. `/habits/history` → `pages/HistoryPage.tsx` is the whole statement (`hooks/useLedger.ts`, `GET /api/Habits/Ledger`, paged, optional `habitId`), rendered by `components/LedgerList/` with titles, icons and deltas from `utils/ledgerEntry.ts`.
  - **Game moments:** `HabitsLayout` shows `components/GameMomentDialog/` for a knockout or a new level the player hasn't seen, on any tab and whatever caused it (a check-in or the day close while they were away). `utils/gameMoments.ts` decides it: `pendingMoment` (knockout first, from `GET Profile`'s `lastKnockout`, whose ledger id grows; then `profile.level` above the level last seen) against `localStorage['lm-habits-seen-knockout']` / `['lm-habits-seen-level']` (try/catch). A device that never saw a level takes the current one as its baseline (`levelBaseline`, adjusted during render) instead of celebrating it. Knockouts are no longer in the check-in or relapse toasts.
  - **Motion:** every animation sits inside `@media (prefers-reduced-motion: no-preference)` and uses `motion.css` tokens. `HabitCheckItem` pops its box and floats "+N coins" on the tap that checks it in (a timed `celebration` state, keyed so a redo replays it); `PlayerHeader` bumps coins and level when they change and flashes the HP track on a loss (`useChangeCount`, from the previous render; alternating `--hit-0/1` classes restart it without remounting the bar); `GameMomentDialog`'s icon enters, then glows (level up) or shakes (knockout).
  - **Onboarding:** empty states offer starters from `utils/starterTemplates.ts` through `components/StarterSuggestions/`: three easy daily habits with a cue (Today and the habits list) and three rewards (the shop), each opening the form filled (`initialValues` on `HabitFormModal`/`RewardFormModal`) — nothing is created until saved. Today sends the template to `/habits/list` as router state (`HabitsPageState`), which `HabitsPage` reads once and clears. With T1–T9 the Habits MVP is complete; the backlog (push reminders, badges, avatar, per-user time zone, ...) lives in the plan, not here.
  - **Streak motivation:** the toast's second line comes from `checkInHighlight(result)` (knockout, streak milestone "Marco de 7 dias! +25 moedas", level up, freeze earned, joined with " · "; the backend's `milestoneDays`/`milestoneCoins`/`freezesEarned`).
